# Phase 03.1: Close gap ICT-07 banner - Research

**Researched:** 2026-09-06
**Domain:** Zustand selector + React banner wiring for existing ICT rollover math (Next.js 16 / React 19 / lightweight-charts v5)
**Confidence:** HIGH (gap chain verified by direct file reads this session; UI placement is a reasoned recommendation)

## Summary

ICT-07 requires that rollover-corrupted ranges are flagged: raw OHLC never adjusted, a `rolloverSuspect` flag on N×ATR close-to-close jumps, plus contract hint and proximity warning. The math half of this requirement is done and unit-tested; the wiring half is absent end-to-end, which is exactly what the v1.0 milestone audit records (audit §3 ICT-07 "unsatisfied", §5 flow F5 FAIL).

The gap chain breaks in two places, both confirmed against live code this session: (1) no store selector invokes `detectRollover` / `isNearRolloverWeek`, and (2) no banner component exists anywhere. `src/lib/store.ts` imports range, bias, DOL, regime, and levels compute functions but never imports `rollover.ts`; its `DashboardState` selector list ends at `selectLevels` with no `selectRollover`. A repo-wide grep for `banner|Banner` and `rolloverSuspect` finds hits only in `rollover.ts`, `types.ts`, and the rollover unit test — zero component hits. The raw-OHLC half of ICT-07 holds: `parseChartJson` in `src/lib/yahoo.ts` reads only open/high/low/close arrays and never touches `adjclose` (zero `adjclose` hits under `src/`).

**Primary recommendation:** Add a `selectRollover` selector to `src/lib/store.ts` (candles + `computeRegime().atr` + `asOfBaku` + `contractHint` → `detectRollover`, with an honest-degrade guard for `atr <= 0`), and render a `data-slot="rollover-banner"` overlay inside the chart card following the STALE-badge / CLOSED-ribbon overlay pattern from Phase 2. Banner-only scope: defer W1, W2, `stale:true`-on-refresh-failure, and `verify-deploy.sh` extensions to separate passes.

### Pattern 1: Compute → selector → component (the only legal wiring)

**What:** Every ICT flag is derived by a pure function in `src/lib/ict`, exposed through a `useDashboard` selector in `src/lib/store.ts`, and read by a client component. No math in components, no store access in math.
**When to use:** Always — this is the STATE-01 contract. `selectRollover` must follow it.
**Example:**

```typescript
// Source: src/lib/store.ts:172-176 (selectRegime — the closest analog: derives from candles via a pure fn)
selectRegime: () => {
  const { candles } = get();
  if (candles.length === 0) return null;
  return computeRegime(candles);
},
```

```tsx
// Source: components/dashboard/report.tsx:37-45 (component reads selectors, never computes)
const selectBias = useDashboard((s) => s.selectBias);
const selectDOL = useDashboard((s) => s.selectDOL);
const selectRegime = useDashboard((s) => s.selectRegime);
```

The new selector mirrors `selectRegime` exactly:

```typescript
// Skeleton — new code in src/lib/store.ts (ATR comes from computeRegime; guard the thin-history atr:0 case)
selectRollover: () => {
  const { candles, contractHint, asOfBaku } = get();
  if (candles.length === 0) return null;
  const { atr } = computeRegime(candles);
  if (!Number.isFinite(atr) || atr <= 0) return null; // honest degrade, not a false flag
  return detectRollover(candles, atr, asOfBaku, contractHint);
},
```

### Anti-Patterns to Avoid

- **Merging rollover into `deriveStatus`:** `deriveStatus` owns LIVE/STALE/CLOSED freshness truth [VERIFIED: src/lib/freshness.ts:32-46]. A rollover flag is data-integrity, not freshness — merging them makes CLOSED weekends mask rollover and vice versa. Keep derivations independent.
- **Calling `detectRollover` from a component:** breaks STATE-01 and duplicates the ATR sourcing question in every consumer. Selector owns it.
- **Freezing or hiding the chart when flagged:** the tested contract is flag-and-continue — `rollover.test.ts:35-44` proves anchors keep computing off current extremes after the flag fires. The banner annotates; it never blocks rendering.
- **Reading `adjclose` to "fix" the gap:** D-08 forbids it; `parseChartJson` deliberately parses only raw OHLC. Interpolating or adjusting the gap destroys the very signal the banner reports.

## Common Pitfalls

### Pitfall 1: Thin-history `atr: 0` turns the tripwire into a hair-trigger

**What goes wrong:** `computeRegime` honestly degrades on thin history by returning `atr: 0` [VERIFIED: src/lib/ict/regime.ts:44-50]:

```typescript
// Source: src/lib/ict/regime.ts:44-50 (verbatim)
if (closed.length < MIN_CANDLES_FULL) {
  return {
    regime: 'compression',
    rationale: `Insufficient history (${closed.length} of ${MIN_CANDLES_FULL} closed candles): honest degrade to compression until the ATR window fills.`,
    atr: 0,
    avg: 0,
  };
}
```

`detectRollover` computes `tripwire = ROLLOVER_ATR_MULT * atr` [VERIFIED: src/lib/ict/rollover.ts:43], so with `atr = 0` any nonzero close-to-close move fires `rolloverSuspect`.
**Why it happens:** Naively passing `computeRegime(candles).atr` straight into `detectRollover`.
**How to avoid:** Selector returns `null` (banner hidden) when `atr <= 0` or non-finite — honest degrade, matching the regime precedent. Alternatively require `closedOnly(candles).length >= MIN_CANDLES_FULL`; the `atr <= 0` guard is the minimal sufficient form.
**Warning signs:** Banner fires on fresh/empty fixtures in dev; unit test with a 5-candle fixture shows `rolloverSuspect: true`.

### Pitfall 2: `detectRollover` throws on bad ATR — selector must never throw into render

**What goes wrong:** `detectRollover` throws `requires a finite non-negative ATR` for non-finite or negative ATR [VERIFIED: src/lib/ict/rollover.ts:39-41]. A selector that throws breaks every subscribed component render.
**Why it happens:** Passing through an unguarded ATR (e.g. `NaN` from an empty series).
**How to avoid:** The same `Number.isFinite(atr) && atr > 0` guard as Pitfall 1, plus the existing `candles.length === 0 → null` early return (selectRegime precedent, store.ts:172-176).
**Warning signs:** `terminal-shell.test.ts`-style render test crashes instead of showing the empty state.

### Pitfall 3: Banner keyed on the wrong `asOf` (client clock vs store `asOfBaku`)

**What goes wrong:** `proximityWarning` depends on the `asOf` date string (`isNearRolloverWeek(asOf)`). Using `new Date()` inline in the component instead of the store's `asOfBaku` makes the banner disagree with `selectRange` anchors and breaks determinism in tests.
**Why it happens:** Copying the StatusStrip local-`now` pattern (status-strip.tsx:15-20 ticks a local clock) where a derived value is needed.
**How to avoid:** Selector takes `asOfBaku` from store state (`get().asOfBaku`, refreshed on each envelope in store.ts:116) — the same date `selectRange` uses (store.ts:134-138). Components never compute dates.
**Warning signs:** Banner proximity text flickers across midnight Baku time or differs between test runs.

### Pitfall 4: Overwriting the forming-candle exclusion

**What goes wrong:** `detectRollover` already excludes forming candles via `closedOnly` [VERIFIED: src/lib/ict/rollover.ts:42]. A selector that pre-filters differently (or passes only closed candles plus re-adds forming) double-handles the W1 skew question.
**Why it happens:** Confusing this phase with W1 (`selectLastClose` forming-close skew — explicitly OUT of scope).
**How to avoid:** Pass full `get().candles` untouched; let `detectRollover` apply `closedOnly` internally. Do not touch `selectLastClose`.
